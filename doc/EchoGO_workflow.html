1 Before you start: what goes into input/

EchoGO supports two input layouts:

1.1 1) Classic / de novo transcriptome layout (Trinity + Trinotate + GOseq)

This is the original EchoGO workflow. It assumes you have already run a Trinity → Trinotate → GOseq pipeline (or an equivalent RNA-seq workflow) and that you have:

  • a count matrix (e.g. Trinity/edgeR/DESeq2 output),
  • one or more differential expression (DE) tables, and
  • a Trinotate report with functional annotation and GO terms.

A typical Trinity/Trinotate/GOseq pipeline is documented at:

https://github.com/trinityrnaseq/trinityrnaseq/wiki

EchoGO does not run Trinity or Trinotate for you. Instead, it takes their outputs (plus GOseq results if you generated them) and performs:

  • matched organism-context enrichment via g:Profiler,
  • conservative/background-aware and exploratory prioritisation,
  • semantic reduction with RRvGO, and
  • GO term network analysis.

1.2 2) Reference-based RNA-seq layout (DESeq2 + GOseq precomputed)

EchoGO can also run from a reference-based experiment folder where GOseq has already been computed. A reference-based EchoGO input directory typically contains:

  • allcounts_table.txt (count matrix; required by the current input resolver)
  • dge_<CONTRAST>.csv (DESeq2 results; one per contrast)
  • dge_<CONTRAST>.GOseq.enriched.tsv (GOseq enriched categories)
  • dge_<CONTRAST>.GOseq.depleted.tsv (optional; only if depleted terms exist)
  • Trinotate_for_EchoGO.tsv (minimal “Trinotate-like” table used by EchoGO)
  • <reference_label>_eggNOG_for_EchoGO.tsv (species-labeled eggNOG table used by EchoGO)

In this mode, GOseq gene_ids may already be gene symbols rather than transcript IDs. EchoGO preserves those values as GOseq display names. g:Profiler submission still uses the portable canonical-name resolver.

To generate this complete reference-based input bundle (including the external eggNOG-mapper step), follow the dedicated vignette:

  • vignette("reference-based-inputs", package = "EchoGO")

When you use echogo_scaffold("my_project"), the input/_README.txt explains both layouts and the expected filenames.

🐙 🦋 🐸 🐟 Cross-Species Consensus Enrichment 🦐 🐍 🦉 🦇

EchoGO is a toolkit for multi-context functional enrichment analysis. Whether you’re working with transcriptomes, proteomes, or ranked gene lists from model organisms or de novo assemblies, EchoGO integrates bias-corrected enrichment (GOseq), matched experiment-derived g:Profiler organism-context runs, semantic reduction (RRvGO), and network analysis in one reproducible workflow.

This vignette covers:

  • Installing and configuring EchoGO
  • Setting up your data and choosing species
  • Running the full end-to-end pipeline
  • Understanding the output structure
  • Exploring results with minimal working examples

For detailed interpretation of outputs, consensus scores, RRvGO, and networks, see vignette("EchoGO_interpretation").

echogo_open_demo()  # Opens demo input/results and lists key files

4 Configuring EchoGO

4.1 Default OrgDb and species

EchoGO uses global options to set defaults:

# Check current defaults
default_orgdb <- getOption("EchoGO.default_orgdb", "org.Mm.eg.db")
default_species <- getOption(
  "EchoGO.default_species",
  c("hsapiens", "mmusculus", "drerio",
    "btaurus", "rnorvegicus",
    "dmelanogaster", "ggallus")
)

cat("Default OrgDb:", default_orgdb, "\n")
#> Default OrgDb: org.Mm.eg.db
cat("Default species:", paste(default_species, collapse = ", "), "\n")
#> Default species: hsapiens, mmusculus, drerio, btaurus, rnorvegicus, dmelanogaster, ggallus

4.1.1 Changing defaults

# Use human genome + fewer species for a quick run
options(EchoGO.default_orgdb   = "org.Hs.eg.db")
options(EchoGO.default_species = c("hsapiens", "mmusculus", "drerio"))

5 Choosing species

5.1 Interactive species picker

The easiest way to choose species is the interactive picker:

echogo_pick_species()

This opens an interactive table where you can:

  • Browse the full g:Profiler organism list
  • Filter by taxonomy (e.g., “Mammals”, “Fish”, “Invertebrates”)
  • Select and copy organism IDs
  • Validate your choices

5.2 Validating species codes

Before running the full pipeline, validate your species choices:

my_species <- c("hsapiens", "mmusculus", "drerio")

# Check if all species are recognized by g:Profiler
echogo_preflight_species(my_species)

If any species codes are invalid, you’ll get suggestions for similar names.

6 Running the pipeline

You have three main ways to run EchoGO:

  1. Quick demo with built-in data (echogo_quickstart())
  2. Scaffold-based run using echogo_scaffold() + echogo_run()
  3. Low-level control with run_full_echogo()

6.1 Option 1: Quick start with demo data

The fastest way to see how EchoGO works is the demo:

# Run the built-in demo (small subset, 3 species + default OrgDb)
echogo_quickstart(run_demo = TRUE)

This runs on a small subset using the default configuration and produces a complete set of outputs in the demo results directory.

The default quickstart is deterministic and offline: it uses cached demonstration responses whose metadata identifies them as a fixture. To test the live service, use echogo_quickstart(run_demo = TRUE, live_gprofiler = TRUE).

6.2 Option 2: Create a project scaffold

For your own data:

# Create a new project directory with input/output structure
echogo_scaffold("my_project")

This creates:

my_project/
  ├── input/
  │   ├── _README.txt          (Instructions for input files)
  │   └── ...                  (GOseq, DE, annotation files, counts matrix)
  └── results/                 (Will be created after run)

The exact expected inputs are described in input/_README.txt. In the Trinity/Trinotate/GOseq mode, the core files are:

  • gene.counts.matrix.tsv – gene-level count matrix (ID + sample columns)
  • DE_*.tsv – one or more DE result tables with at least id, log2FC, pvalue, padj
  • Trinotate.xls – standard Trinotate report with GO terms and KEGG IDs

EchoGO reads these files, matches IDs across them, and uses Trinotate GO/KEGG annotations for GOseq and portable names for organism-context enrichment.

6.3 Option 3a: Run the scaffolded workflow with echogo_run()

Once your input is ready:

echogo_run(
  input_dir = "my_project/input",
  outdir    = "my_project/results"
)

echogo_run() is a convenience wrapper that:

  • Respects your EchoGO.default_species and EchoGO.default_orgdb options
  • Infers which inputs are present (GOseq, DE, annotations, counts)
  • Calls run_full_echogo() with reasonable defaults

Values supplied directly to echogo_run(), such as make_report = FALSE or run_rrvgo = FALSE, override the scaffold defaults. HTML report generation requires Pandoc; verify rmarkdown::pandoc_available() when running R outside RStudio.

6.4 Option 3b: Run the full workflow explicitly

If you want full control, call run_full_echogo() directly:

run_full_echogo(
  input_dir   = "my_project/input",
  species     = c("hsapiens", "mmusculus", "drerio"),
  orgdb       = "org.Hs.eg.db",
  outdir      = "my_project/results",
  make_report = TRUE
)

6.5 Option 3c: Reference-based RNA-seq run (DESeq2 + GOseq precomputed)

If your input directory already contains precomputed GOseq enrichment tables and the minimal Trinotate-like + eggNOG annotation tables (reference-based workflow), you can run EchoGO directly from that folder.

If you need to generate those inputs from a reference genome (GFF3 + protein FASTA), see the reference-based input vignette.

The recommended entry point is resumable around the external eggNOG-mapper step:

prep <- echogo_prepare_reference_inputs(
  root = "path/to/reference_project",
  gff_file = "genome.gff3.gz",
  protein_fasta = "proteins.faa.gz",
  reference_label = "MySpecies",
  orgdb = NULL
)

# Run the command in prep$emapper_command, then repeat the same call.
prep$status
input_dir <- "path/to/reference_project/echogo_input"
outdir    <- "path/to/reference_project/echogo_results"

fish_species <- c(
  "drerio", "strutta", "gaculeatus", "olatipes", "trubripes", "amexicanus",
  "oniloticus", "ssalar", "omykiss", "okisutch", "otshawytscha"
)

res <- run_full_echogo(
  input_dir              = input_dir,
  species                = fish_species,
  orgdb                  = "org.Dr.eg.db",
  outdir                 = outdir,
  strict_only            = FALSE,
  run_evaluation         = TRUE,
  make_report            = TRUE,
  verbose                = TRUE
)

6.5.1 Key parameters

  • input_dir – path containing your input files (see _README.txt in the scaffold).
  • species – character vector of g:Profiler organism codes.
  • orgdb – OrgDb package used for GO structure and semantic similarity (e.g. "org.Mm.eg.db").
  • outdir – where to save all results.
  • make_report – if TRUE, generates an interactive HTML report (Rmarkdown).

6.5.2 Under the hood

Before enrichment, EchoGO creates one matched gene-set pair for each contrast. The foreground is selected from significant rows in the DE table; the background is the tested experiment universe. An explicit logical significance column is used when present, otherwise the default rule is padj <= 0.05 and abs(log2FoldChange) >= 1. Missing adjusted p-values do not pass. A DE file declared significant-only requires the count matrix or an explicit tested-gene list to supply the larger universe.

Foreground and background pass through the same deterministic portable-name resolver. Its priority is: genuine SwissProt gene symbol, EggNM.Preferred_name, then a portable native symbol. Raw transcript/contig IDs, eggNOG seed orthologs, species-prefixed Ensembl protein IDs, and arbitrary accessions remain in the mapping audit but are not submitted. Duplicate names collapse by stable first occurrence. Taxonomy labels are provenance only and are not treated as numeric eligibility cutoffs. The resolved foreground must be a non-degenerate subset of the resolved background. EchoGO submits the same resolved vectors independently under each organism code. This is organism-context analysis, not explicit species-specific ortholog mapping. Mapping audits, exact vectors, hashes, and per-run response metadata are saved below gprofiler/.

run_full_echogo() orchestrates:

  1. GOseq enrichment (bias-corrected via gene length) if requested and inputs are available
  2. g:Profiler with custom background (primary background-aware organism-context enrichment)
  3. g:Profiler genome-wide (exploratory, no background)
  4. Consensus scoring (via score_consensus_terms())
  5. RRvGO reduction (clusters semantically similar terms)
  6. Network analysis (gene-overlap GO term networks)
  7. Report generation (if make_report = TRUE)

7.1 Directory guide

7.1.1 consensus/

Start here. Contains annotated consensus tables and curated plots.

  • consensus_enrichment_results_with_and_without_bg.xlsx – main results table
  • plots_strict/ – visualizations using the conservative/background-aware score (consensus_score)
  • plots_exploratory/ – visualizations using exploratory consensus (consensus_score_all)

7.1.2 diagnostics/ & evaluation/

Quality control and diagnostic plots:

  • EQI_distribution_by_ontology.png – term agreement quality
  • FoldEnrichment_distribution_by_ontology.png – enrichment magnitude
  • rarefaction_curve_by_origin_*.png – saturation curves (methods/species)

7.1.3 goseq/

Bias-aware GOseq enrichment results:

  • GOseq_enrichment_full_annotated.csv – full GOseq output with annotations

7.1.4 gprofiler/

Raw g:Profiler results (one folder per species or background mode):

  • with_custom_background/ – conservative, background-corrected results
  • no_background_genome_wide/ – exploratory, genome-wide results

7.1.5 rrvgo/

Semantic similarity reduction (per ontology BP/MF/CC):

  • rrvgo_true_consensus_with_bg/ – background-aware clusters (compatibility-only legacy folder name)
  • rrvgo_exploratory_all_significant/ – all significant terms clustered

These folders typically contain:

  • Treemaps, bubble plots, heatmaps, wordclouds
  • Cluster summary tables
  • Representative term lists per cluster

7.1.6 networks/

GO term overlap networks:

  • with_bg/ – background-aware consensus networks
  • with_bg_and_nobg/ – exploratory networks

Each contains networks for BP, MF, and CC (static PDF/SVG + interactive HTML).

7.1.7 report/

Interactive HTML report (if make_report = TRUE):

  • EchoGO_report.html or index.html – browse-friendly summary of all results

For a deep dive into what each file means and how the consensus scores are built, see vignette("EchoGO_interpretation").

8.1.1 What these columns mean (briefly)

  • term_id – GO or KEGG identifier (e.g., "GO:0006355")
  • term_name – human-readable name
  • ontology – BP (Biological Process), MF (Molecular Function), or CC (Cellular Component)

  • consensus_score_all – exploratory score (includes genome-wide g:Profiler)
  • source_origin – combination of sources (GOseq, g:Profiler with/without background)
  • significant_in_any – TRUE if any method supports the term

For full details and biological interpretation, see vignette("EchoGO_interpretation").

12 Troubleshooting

12.1 OrgDb not found

Error: OrgDb 'org.Mm.eg.db' not installed

Solution:

echogo_install_orgdb("org.Mm.eg.db")
echogo_require_orgdb("org.Mm.eg.db")

12.2 Species code not recognized

Warning: Species 'human' not recognized

Solution: Use the interactive picker or check the full list at
https://biit.cs.ut.ee/gprofiler/page/organism-list

echogo_preflight_species("hsapiens")  # Use proper code, not common name

12.3 g:Profiler timeout

If you have a very large species list or gene set, g:Profiler may time out. Try:

  • Reducing the number of species
  • Splitting your gene list into smaller subsets
  • Increasing timeout, e.g.:
options(EchoGO.gprofiler_timeout = 120)
